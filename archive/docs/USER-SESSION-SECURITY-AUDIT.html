Executive Summary

Atlas has a real, purpose-built authentication system — not a placeholder. Password hashing, HMAC-signed cookies, session lifecycle, audit logging, and demo patient isolation are all correctly implemented. The foundations are strong.

However, several production blockers exist that must be resolved before real users with identifiable health data can be onboarded. The most critical are: no rate limiting on login/signup, seven unprotected internal API routers, and no email verification. These are well-understood problems with straightforward fixes — none require architectural rework.

On the demo user question: the current model (demo sessions as user_id=NULL rows in the sessions table) is clean, secure, and appropriate for the current scale. The main practical argument for promoting demo users to first-class accounts is enabling workspace persistence across visits and an upgrade/conversion flow — not security. This report recommends deferring that change until the production auth system is fully hardened.

i
Synthea data only — not real PHI

All data currently in the system is algorithmically generated by the Synthea simulator. The privacy stakes are low today. The recommendations in this report are written for the production state where real patient data will be onboarded.

Password Storage

Passwords hashed with scrypt (N=16384, r=8, p=1, 16-byte random salt). Format: scrypt$16384$8$1$<b64_salt>$<b64_digest>. Verification uses hmac.compare_digest — constant-time, no timing oracle.

!
scrypt N=2^14 is below current OWASP recommendations

OWASP recommends N=2^15 (32768) as the minimum for 2024+. Fix: lazy migration — rehash at higher cost on the next successful login. Not a blocker but should be done before real PHI enters the system.

Bootstrap Account

_seed_bootstrap_user() runs at every startup. In development, creates a clinician-role account with a hardcoded password of "atlas-demo-password" if EHI_AUTH_BOOTSTRAP_PASSWORD is not set. In production (ENVIRONMENT=prod) seeding is skipped if no env var is set — but no deployment check verifies the admin account was properly provisioned.

Session Cookie

Cookie: atlas_session = <session_id>.<HMAC-SHA256>. Secret from data/atlas-session.key (auto-generated 32 random bytes) or EHI_SESSION_SECRET env var. Flags: HttpOnly=True, Secure=True in production (env-gated), SameSite=lax, Max-Age=7 days.

Frontend Session Handling

Architecture

All auth state lives in AccessContext (app/src/context/AccessContext.tsx) — single source of truth for mode, user identity, active patient, and all mutations. In production, no auth data is written to localStorage. The session is entirely server-side (HTTP-only cookie). The frontend re-hydrates by calling GET /api/auth/session on mount.

Demo Session Architecture

Demo mode is a first-class session mode, not a separate deployment. It creates a real row in the sessions table with mode="demo" and user_id=NULL. The cookie is identical to an authenticated session.

How It Works

  1. Visitor calls POST /api/auth/demo { patient_id: "demo-high-risk" }
  2. Backend validates alias against hardcoded DEMO_PATIENTS allowlist; invalid IDs get HTTP 403
  3. Session row created with user_id=NULL; atlas_session cookie set
  4. On every patient data request, authorize_patient_access() checks session.is_demo and resolves alias to real Synthea UUID
  5. Patient list returns only the 3 demo aliases; full corpus is never surfaced

Critical Findings — Production Blockers

These must be resolved before real users with identifiable health data are onboarded.

C1
No rate limiting on authentication endpoints
api/routers/auth.py · POST /login, /signup, /demo
Critical
Zero brute-force protection. An attacker can send unlimited login attempts to enumerate valid emails and crack passwords. Fix: add slowapi or a Redis-backed counter — 5 attempts per email per 15 minutes, exponential backoff, lockout with Retry-After header.
C2
Seven API routers have no authentication check
api/routers/corpus.py · harmonize.py · classifications.py · pipeline_lab.py · ground_truth_review.py · ccda.py · and others
Critical
Unprotected routes include: /api/corpus/* (full CSV/ZIP export of all patient data), /api/harmonize/* (all harmonization collections), /api/classifications/* (raw FHIR by patient ID), /api/pipeline-lab/*, /api/ground-truth-review/*, /api/internal/ccda-lab/*. Fix: add require_authenticated_session to all. For internal routes, consider restricting via nginx to the internal network only.
C3
No email verification before PHI access
api/core/auth.py · signup flow
Critical
Any email address creates a fully active account immediately; a session is returned with the signup response. Fix: add status='pending_verification', a time-limited HMAC-signed email token, and gate patient data access on status='active' only.
C4
No password reset flow
api/routers/auth.py — endpoint missing entirely
Critical
A locked-out user cannot recover access without direct database manipulation. Fix: POST /api/auth/forgot-password (sends time-limited HMAC token to verified email) + POST /api/auth/reset-password (validates token, sets new hash, invalidates all sessions). Token must be single-use.
C5
Bootstrap account ships with a hardcoded known password
api/core/auth.py · _seed_bootstrap_user()
Critical
When EHI_AUTH_BOOTSTRAP_PASSWORD is not set, the bootstrap account is created with password "atlas-demo-password". Fix: remove the fallback default entirely. Add a startup assertion that fails loudly if ENVIRONMENT=production and the bootstrap password env var is not set.
C6
Guest harmonization files stored in plaintext
api/core/guest_harmonization.py · data/guest-harmonization/
Critical
User-uploaded health records (which may contain real PHI) are written to disk without encryption. Fix: encrypt files at rest using a per-run AES-GCM key derived from the run ID, or enable filesystem-level encryption on the Hetzner data volume.

Important Gaps — Pre-Production Hardening

I1
Session table grows unboundedly — no cleanup job
api/core/auth.py · data/auth.db sessions table
Important
Expired and revoked sessions are marked but never deleted. Add a background task: DELETE FROM sessions WHERE revoked_at IS NOT NULL OR expires_at < datetime('now', '-30 days'). Also define a data retention policy for audit events.
I2
Role-based access control defined but never enforced
api/auth_models.py · AuthRole enum · all routers
Important
Five roles exist (consumer, clinician, attending, coordinator, admin) and are stored correctly. No endpoint checks the role. A consumer has identical access to an admin. Define the access matrix and add a require_role() FastAPI dependency.
I3
Signup UI is a placeholder — backend endpoint is live
app/src/pages/AccountAccess.tsx · api/routers/auth.py POST /signup
Important
The frontend shows "Public account creation is not wired to the backend in this release." The backend POST /api/auth/signup endpoint is fully functional. Either wire the UI or add a feature-flag gate on the backend endpoint. The current mismatch is ambiguous.
I4
Chat history not cleared on logout
app/src/context/AccessContext.tsx · clearAccess()
Important
Caspian AI conversation history (atlas:caspian:assistant:{patientId}:{sessionId}) persists in localStorage after logout. On a shared device the next user can read prior clinical conversations. clearAccess() should purge all atlas:caspian:* and ehi-provider-assistant-* keys.
I5
No session expiry detection in the frontend
app/src/context/AccessContext.tsx
Important
The expiresAt field is stored in AccessState but nothing checks it. When a session expires mid-use, API calls silently fail until the user manually refreshes. Fix: Axios response interceptor that catches 401s and calls refreshSession() or redirects to /account.
I6
No hard frontend route protection
app/src/App.tsx · AppShellRoute
Important
Unauthenticated users navigating directly to /patient-record or /caspian are not redirected — the page renders with empty data. Security relies entirely on the backend. A <RequireAuth> wrapper improves UX and defense-in-depth. Low urgency if backend gates are solid.
I7
Missing security response headers
deploy/nginx-app.conf · deploy/nginx-host.conf · api/main.py
Important
Neither nginx nor FastAPI middleware adds Content-Security-Policy, X-Content-Type-Options: nosniff, or X-Frame-Options: DENY. Add these to the nginx host config before public launch. A restrictive CSP is especially important for a clinical app.

Demo User Architecture — Decision Analysis

Should demo users be modeled as first-class accounts with role="demo" rather than the current user_id=NULL session model?

Option A: Keep demo as a separate mode Recommended for now

Status quo — user_id=NULL sessions, mode="demo"

Pros
  • Zero friction — two clicks to a chart, no email required
  • No user table garbage accumulation
  • Hard, simple security boundary (alias allowlist)
  • No per-user state to clean up on bounce
  • Audit trail still works (events written with null user_id)
Cons
  • No workspace persistence across visits
  • No upgrade path from demo → real account
  • Mode check scattered across routers (manual consistency)

Option B: Demo users as first-class accounts (role="demo")

Auto-create a user row on demo entry; promote on signup

Pros
  • Workspace state persists across visits
  • Clean upgrade path: POST /auth/claim-demo
  • Role-based gate replaces mode-based gate (cleaner long-term)
  • Stable user_id enables cross-visit analytics
Cons
  • User table accumulates throwaway rows
  • Requires background cleanup job for expired demo accounts
  • Patient access restriction still needs same enforcement logic
  • Adds complexity before production auth system is hardened
→
Recommendation: Defer Option B until production auth is hardened

The current demo model is clean and correctly implemented. The benefits of Option B (workspace persistence, upgrade path) are real but not urgent for Phase 1. The production auth blockers are higher priority. Revisit this when the Phase 2 "consumer account" story is designed.
