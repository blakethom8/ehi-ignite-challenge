### 2. Held items (intentionally untouched)

These were called out and intentionally NOT changed in this pass:

- **`ChatWidget.tsx`** is still mounted globally on non-workspace routes (Patient Record, FHIR Charts, Learn). Chat now lives inside `WorkspaceFrame`. The floating widget is potentially redundant; user wanted to think about it before deciding to delete or reposition.
- **`Landing.tsx`** still serves as the marketing entry at `/`. User chose to keep it rather than redirect `/` straight to `/caspian`.

### 3. The architecture promise the UI is making is NOT yet enforced

Read `docs/architecture/AGENTIC-HARNESS.md` end-to-end before touching backend. Key gaps:

- `Workspace.family: "clinical" | "plugin"` is the only encoding of the trust posture in code today. It selects a UI variant. It does **not** stop a misconfigured plugin from reading raw FHIR.
- `app/src/components/atlas/trust.ts` declares `PluginManifest`, `AnchorPackage`, `ProvenanceRecord`, divergent approval shapes — but nothing imports these types yet. They're a stub for the next backend integration to build against.
- `api/` has zero plugin-runtime awareness. No manifest verification, no anchor compilation, no consent gate, no provenance log. The marketplace UI is currently theatre at the runtime layer.

### 4. Next-priority builds (in order)

1. **Wire `trust.ts` types into the existing fixture path.** `components/atlas/data.ts` should declare each plugin's `PluginManifest` (`id`, `version`, `vendor`, `permissions`, `connectors`, `requiresConsent`). The `PluginHome` permissions ledger should render from the manifest, not from a hardcoded array.
2. **Sketch `api/trust/models.py`** as the Pydantic mirror of `trust.ts`. No endpoints yet — just the models, with verification helper stubs.
3. **First real consent-gate flow.** Pick one outbound action (the Trial Finder packet send), wire it through an `ApprovalCard` that posts a `PluginApprovalRequest`, blocks on it, and writes a `ProvenanceRecord` to a SQLite table when approved.
4. **Anchor compilation.** Stop having plugins read `PATIENT` from `data.ts`. Compile a per-run anchor server-side (with the plugin's declared `scope`), sign it, and have the frontend hand it to the workspace as the only patient handle the plugin can see.
5. **Backend folder split** per AGENTIC-HARNESS.md §5: `api/workspace/`, `api/caspian/`, `api/plugins/`, `api/trust/`. Move existing routers into `api/workspace/` if they're shared; create empty `api/plugins/` directory with `manifest.py`, `anchors.py`, `consent_gate.py`, `provenance.py` stubs.

### 5. Open product/architecture questions (from AGENTIC-HARNESS.md §9)

These deserve answers before plugins go past stub:
1. Sandbox model — in-process capability check, separate worker, or container?
2. Anchor refresh — what happens when Caspian updates state mid-plugin-run?
3. Vendor identity attestation — self-sign, federate, or per-org?
4. Plugin-to-plugin composition — allowed? Provenance chain rules?
5. Caspian-as-publisher — first-party plugin tier?
