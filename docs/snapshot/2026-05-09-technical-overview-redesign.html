Website redesign · Technical Overview section

From "Data Labs" to a Technical Overview that earns trust

2026-05-09 · proposed IA + naming + content sketch · before any code

The current /analysis/* section is six developer-facing pages organized by what data shows. The new section should be organized by what visitors want to know, with the same rigor as the Phase 1 submission narrative but in a browseable, web-native form. Below: who it's for, the IA I'd build, naming options, and what the page-level content sketch looks like.

§1Current state — what's there now

Six pages live at /analysis/*:

  • /analysis (Overview) — stat tiles, learning objectives, pipeline steps, question-to-resource map
  • /analysis/fhir-primer — explainer on FHIR R4 resource types
  • /analysis/methodology — pipeline stages and trust gates
  • /analysis/definitions — field-by-field reference
  • /analysis/coverage — corpus-level coverage stats
  • /analysis/flight-school — onboarding/orientation content

The pages exist and have content, but the section as a whole reads as a methodology reference for someone already inside the project. A first-time visitor — judge, health-IT vendor, clinician — doesn't know whether to start with FHIR Primer, Methodology, or Overview. There's no visible argument structure: "here's what we built, here's why, here's how to evaluate it."

Three structural problems:

  1. Organized by data, not by question. "Coverage" and "Definitions" answer reference questions. Visitors come with strategic questions: "is this real?", "how does it work?", "what makes it trustworthy?", "how does it compare to X?"
  2. The PDF lab — the most differentiated technical work — isn't surfaced. The whole bake-off, the gold-standard methodology, the live F1 numbers, the local-Gemma experiment — none of it appears in this section.
  3. The submission's strongest arguments aren't reflected. The "we sit alongside TEFCA" framing, the four trust guardrails, the provenance wedge, the harmonization story — the website doesn't echo these.

§2Who is this section actually for?

Four real audiences, in rough order of "would they actually click into this section?":

Phase 1 / 2 judges

EHIgnite reviewers, ONC-affiliated

Want to verify the submission is real. Will check whether the website corroborates the PDF — or contradicts it. Care about evidence, methodology, honesty about limitations.

Health-IT-literate visitors

Devs, vendors, FHIR-fluent

Want to evaluate whether you understand the ecosystem (CCDA, US Core, TEFCA). Will look for specifics: which FHIR profile, which converter, which standards.

Clinical evaluators

Physicians, informaticists

Want to understand how trust is built. Care about deterministic-first logic, citations, missing-information disclosure, and whether the AI can be safely used in care.

Future collaborators

Phase 2 partners, researchers

Want to know if the platform is something they could build on or contribute to. Care about modularity, extensibility, the wedge.

Patients/caregivers are not the audience for this section. They have other surfaces (the explorer, the assistant, the patient-journey app). The Technical Overview is for people who want to understand the engine.

My pick: "How It Works" as the menu name, with the URL /how-it-works. The page titles inside ("How does data flow...", "How do we extract...", etc.) all start with "how" — which makes the section internally coherent and signals from the menu what kind of content this is. "Methodology" is a fine alternative if you want a more clinical voice; less inviting but more credible. Avoid "Technical Overview" / "The Stack" — both narrow the audience.

§5Visual / page-shape principles

Three rules for each new page so they stay coherent and don't drift back into card-sprawl:

  1. Lead with the question, not a hero card. The page title is the question. The first paragraph answers it in 2-3 sentences. Everything below is supporting evidence.
  2. Show, don't list. Each page should embed at least one live thing — a screenshot from the app, a code-shaped tool example, a real F1 number, a snippet of an actual evidence packet. Generic feature-list cards are the failure mode.
  3. Honesty about limits. Each page has a "What this doesn't yet do" or "Phase 2 next steps" section near the bottom. This is the single biggest credibility lever. Judges and health-IT vendors trust submissions that name their limits more than ones that don't.
