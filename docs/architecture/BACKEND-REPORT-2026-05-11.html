The Atlas backend is substantially more complete than the architecture docs suggest. As of commit f4265e3, 18 routers are fully implemented (no stubs), the plugin runtime enforces cryptographic trust boundaries end-to-end, and the SQL-on-FHIR warehouse is live with enrichment and derivation layers. The codebase is production-grade in depth.

The primary gaps for production are operational, not functional: no CI/CD pipeline, LLM tracing disabled by default, plugin connectors running on fixtures instead of real HTTP adapters, and the anchor compiler reading demo patient fixtures rather than live FHIR data. The context engineering Layer 2 (LLM batch enrichment) — the product's core differentiator — is also explicitly deferred to Phase 2 and should be the first engineering investment post-submission.

Phase 1 deadline in 2 days. No new features should be started before submission. The 15 recommendations below are sequenced for the post-submission window, not the immediate sprint.

2. Architecture Overview

Atlas is a shared agentic harness with two distinct workspace families. The backend enforces the trust contract that the UI's boundary pills advertise.

Caspian — First-Party Clinical

  • Direct SQL-on-FHIR access (full chart)
  • 4 assistant modes: deterministic, context, agent_sdk, cursor
  • 5-layer context engineering pipeline (Layers 0–1, 3–4 live; Layer 2 deferred)
  • Skills runtime with workspace + agent loop
  • Clinical audit log via tracing.py
  • Harmonization + provenance graph

Plugins — Consented External

  • Signed manifest verification (ed25519)
  • Scope-projected, redacted anchor packages
  • Run-level consent gate + per-action approvals
  • 22 tool handlers across 3 installed plugins
  • Append-only provenance log (signed)
  • 3 installed: trial-finder, med-access, second-opinion

Shared Infrastructure

  • FastAPI + uvicorn (port 8000)
  • Session-based auth (SQLite auth.db)
  • SQL-on-FHIR warehouse (data/sof.db)
  • lib/fhir_parser — PatientRecord model
  • lib/clinical — drug classifier + episodes
  • Tracing spans (SQLite + Langfuse opt-in)
  • Docker Compose + nginx (Hetzner)
  • ed25519 signing (Atlas key + vendor keys)
  • 1,180 Synthea FHIR bundles

Request Path — Caspian Assistant

Browser POST /api/assistant/chat
  → TracingMiddleware (opens trace, captures patient_id + question)
  → require_access_session() (validates session cookie)
  → provider_assistant_service.answer_provider_question()
      ↳ mode=context      → context_builder.build_clinical_context() → Claude API (single turn)
      ↳ mode=agent_sdk    → sof_tools.run_sql() + FHIR tools → Agent SDK loop
      ↳ mode=deterministic → keyword ranking + FHIR facts (no LLM)
      ↳ mode=cursor       → cursor_sidecar HTTP client
  → TracingMiddleware (flushes trace + optional Langfuse export)
  ← AssistantResult {answer, confidence, citations, follow_ups, engine}

Request Path — Plugin Tool Call

Browser POST /api/plugins/runs/{run_id}/tool/{tool_id}
  → require_access_session()
  → plugin_runtime.call_tool(run_id, tool_id, payload)
      → _require_consent(ctx)              # consent token valid + not revoked?
      → _manifest_declares(manifest, tool_id)  # tool in manifest?
      → dispatch_tool(tool_id, ctx, payload)
          ↳ read-anchor:    verify scope → read_anchor_field() [OutOfScope → 403]
          ↳ call-external:  verify connector declared → connector.call()
          ↳ send-outbound:  approved_outbound=True required → write ProvenanceRecord
  ← tool result dict

Skills Runtime

The skills runtime (api/core/skills/) is the most sophisticated subsystem in the codebase. It is a two-layer architecture:

  • 1
    Workspace layer (workspace.py, ~1200 LOC) — per-run directory at data/cases/{patient_id}/{skill}/{run_id}/. Mediated writes, citation tracking (c_XXXX IDs), escalation gates (a_XXXX approvals), save destinations (run / patient memory / package). Enforces full audit trail of every agent action.
  • 2
    Agent loop layer (agent_loop.py, ~600 LOC) — multi-turn Claude loop. Tool registry with workspace_write, workspace_cite, workspace_escalate, clinicaltrials_search, submit_final_artifact, canvas_upsert. Configurable max_turns (30) and tokens per turn (4096).
api/workspace/ is absent. The AGENTIC-HARNESS.md spec defines a shared workspace module at api/workspace/ (sessions, events, artifacts, tool envelope). This directory does not exist. Caspian and plugins each maintain their own session/event/artifact systems separately. This is the largest structural divergence from the spec, and the right time to unify is before Phase 2 adds more plugins.

Security Model — Two Gate Enforcement

Rule 1: "A plugin reads nothing outside its anchor scope"
  Gate A (manifest-level): tool declared? permission = read-anchor? field in manifest.anchor.fields?
  Gate B (anchor-level):   read_anchor_field(pkg, field) → raises OutOfScope if field not in pkg.scope
  Both gates must pass. Belt-and-suspenders.

Rule 2: "A plugin writes nothing outbound without consent + per-action approval"
  Consent token: minted at run start, TTL-checked on every call, revocable mid-run.
  Per-action: send-outbound tools require approved_outbound=True → dispatched only after ApprovalCard.
  Provenance row written after every outbound action (vendor, version, approver, redaction preset, endpoint).

Run State Machine

start_run() → [awaiting-consent] → grant_consent() → [running]
                                                           ↓
                                              request_outbound_approval() → [waiting]
                                                           ↓
                              approve_outbound() → [running]   deny_outbound() → [running]
                                                           ↓
                                              complete_run() → [complete]
* ─────────────────── revoke_consent() → [revoked] (voids all pending approvals, any state)
Anchor v1 limitation: anchors.py compiles from 4 demo patient fixtures (canned JSON), not live FHIR data. The scope enforcement is cryptographically real — but the patient data behind the anchor is synthetic. This is the most critical plugin gap before any real-world clinical use.

7. Production Recommendations

Sequenced by risk and impact. Critical items block production readiness. High items should be resolved in the first two weeks post-submission. Nothing below should be started before Phase 1 ships on May 13.

Critical — Block Production

1. Wire anchor compiler to live FHIR data

Critical

The plugin anchor compiler (anchors.py → _load_patient_slice()) reads 4 canned demo patient fixtures. Every real plugin run produces an anchor backed by synthetic data, not the actual patient record. The scope enforcement is cryptographically sound — but it's enforcing access to fake data. Wire compile_anchor_package() to load from lib/fhir_parser.bundle_parser.parse_bundle() using the real patient ID.

api/plugins/anchors.py → compile_anchor_package() → replace fixture lookup with parse_bundle(patient_id)
Why critical: plugins are the flagship marketplace story. A demo running on fake data is a demo — real clinical value requires real data.

2. Add CI/CD pipeline

Critical

All deployments are manual SSH to deploy-prod.sh. There are no automated tests running on push, no build validation, no rollback strategy. A broken commit merged to master can silently break production. At minimum: run pytest + npm run build on every PR (block merges on failure), and gate the production deploy on passing health checks.

.github/workflows/ci.yml (pytest + tsc + build) · .github/workflows/deploy.yml (ssh + health gate)
Why critical: one broken push can take down the demo during the judge review window.

3. Move secrets out of plaintext key files

Critical

Three signing/session keys live as plaintext files in data/ (atlas-signing.key, atlas-session.key, atlas-guest-harmonization.key). Any backup, log collection, or Docker volume exposure that touches data/ can leak these. Load them exclusively from environment variables (ATLAS_SIGNING_KEY, EHI_SESSION_SECRET) in production with no file fallback.

api/trust/keys.py → atlas_keypair() · api/core/auth.py → init_auth_store()
Why critical: the Atlas signing key is the root of the plugin trust chain. Compromise = forged vendor manifests.

4. Persist consent revocation across restarts

Critical

The _revoked_ids: set[str] in runtime.py is in-memory. An API restart (deploy, crash) silently forgets all revocations. A clinician who revoked a plugin's consent mid-run would have that revocation erased — the plugin could call tools again as if consent was never withdrawn. Add a revoked_at column to the runs table in data/runs.db and reload into the in-memory set on startup.

api/plugins/runtime.py → _revoked_ids · persist to data/runs.db · reload on init
Why critical: consent revocation is a patient safety control. Making it transient defeats the design.

High — First Two Weeks Post-Submission

5. Build Layer 2: LLM Batch Enrichment

High

The context engineering pipeline (Layers 0–1, 3–4) is live but Layer 2 — the product's core competitive differentiator — is explicitly TODO. This is where an LLM pre-processes clinical episodes to produce relevance scores, clinical narratives, cross-episode relationship detection, and reclassified markdown rows that make the "right 5 facts in 30 seconds" promise real. The economic model is compelling: ~$0.01–$0.05 per patient one-time via Haiku, cached and reused across all conversations.

api/core/temporal.py (temporal metadata) → api/core/batch_enrichment.py (Haiku batch calls) → wire into context_builder.py Layer 2 slot
Why high: without Layer 2, Caspian gives a good briefing. With it, Caspian gives a clinically differentiated briefing that rules can't replicate.

6. Create api/workspace/ — shared session and event primitives

High

The AGENTIC-HARNESS.md spec defines a shared workspace module at api/workspace/ (sessions.py, events.py, artifacts.py, tools/envelope.py) used by both Caspian and plugins. This directory does not exist. Both families maintain separate session/event/artifact implementations. Before a fourth or fifth plugin is added, extract the shared protocol into a dedicated module so all workspaces build on the same primitives and the tool-call envelope is consistent.

Create api/workspace/ · refactor api/plugins/runtime.py + api/core/skills/ to share sessions + events
Why high: structural debt compounds with every new plugin. Three plugins is the right inflection point.

7. Enable tracing in production with sampling

High

LLM tracing is off by default. In production this means zero cost visibility, no latency data, no quality monitoring. Enable with a configurable sample rate (start at 100%, drop to 20% when traffic grows). Also extend TracingMiddleware beyond /api/assistant/chat to cover skill runs and plugin tool calls — those are the most expensive operations and currently completely unobserved.

Set TRACING_ENABLED=true · add TRACING_SAMPLE_RATE env var · extend TracingMiddleware to skills + plugins
Why high: you can't optimize token costs or catch hallucinations without data. This should be on from day one of real use.

8. Replace fixture-based plugin connectors with HTTP adapters

High

Plugin connectors (api/plugins/connectors.py) route calls to fixture JSON files. The code comments label this "v1" with "v2: real HTTP adapters" deferred. Real-world plugin use requires actual HTTP calls to ClinicalTrials.gov, payer formulary APIs, and referral networks. The connector registry architecture is solid — just swap fixture reads for httpx async calls with proper timeout and error mapping.

api/plugins/connectors.py → replace _load_fixture() calls with async httpx.get/post
Why high: trial-finder "sends to ClinicalTrials.gov" is currently fiction. The demo works; production doesn't.

9. Add SQLite schema versioning

High

Five SQLite databases auto-create their schema on first use with no version tracking (sof.db, traces.db, auth.db, runs.db, provenance.db). Any column addition requires either a migration script or a destructive reset. Add a schema_version table and a minimal migration runner per database. Start with runs.db and traces.db — they evolve most frequently as new features ship.

data/migrations/ folder per db · schema_version table · apply on startup before app init
Why high: production databases accumulate data. Schema drift without migrations means destructive resets or silent bugs.

Medium — Before Phase 2 GA

10. Complete Agent SDK assistant mode

Medium

The agent_sdk mode has infrastructure wired (imports, tool shims, SDK config, claude-agent-sdk 3.4.7 in lockfile) but the main agent loop is partially implemented. This is the most powerful mode — multi-turn reasoning with run_sql access — and where complex clinical questions get properly answered. Complete provider_assistant_agent_sdk.py → answer_with_agent_sdk() and add a trace-level eval harness to benchmark against the context mode baseline.

api/core/provider_assistant_agent_sdk.py

11. Add plugin sandbox (process-level isolation)

Medium

Plugin tools currently run in-process. A buggy or malicious plugin handler could read process memory, import internal modules, or corrupt shared state. Add subprocess-level isolation (separate Python process per run, IPC over JSON) or a capability-checked in-process sandbox (restricted builtins + import blocking via RestrictedPython). The latter is simpler for Phase 2 and buys 80% of the isolation guarantee.

api/plugins/sandbox.py (does not exist) · wrap dispatch_tool() call

12. Upgrade Hetzner to CX31 and add uptime monitoring

Medium

The production server is CX21 (4 GB RAM). Running 5 containers — including a FHIR converter at ~1.5 GB RSS and SOF warehouse materialization at startup — is tight. A memory OOM during a judge demo would be catastrophic. Upgrade to CX31 (8 GB, ~€9/mo). Also add an uptime monitor (UptimeRobot free tier) watching /api/health so any downtime during the review window is caught immediately.

Hetzner console → resize · UptimeRobot → monitor /api/health every 5 min

13. Per-org plugin registry + vendor key rotation

Medium

All installed plugins are currently available to all users and the vendor allowlist is a static JSON file. The AGENTIC-HARNESS.md spec requires per-org enable/disable and versionable upgrades. Add an org-scoped plugin registry table in runs.db and a key rotation flow so vendor keys can be replaced without redeploying. Required before the marketplace story scales to multiple organizations.

api/plugins/registry.py (does not exist) · vendor keys → DB-backed lookup

14. Add FHIR Provenance edges to the gold layer

Medium

The Atlas data model (Decision 5) declares Provenance as the competitive wedge. The harmonization system produces provenance records, but the SQL-on-FHIR gold layer derivations (medication_episode, observation_latest) do not carry bronze_source or bronze_path columns. Without these, the "click any fact → see lineage" UI promise can't be honored from the warehouse. Add provenance columns to lib/sql_on_fhir/derived.py.

lib/sql_on_fhir/derived.py → build_medication_episodes() → add source_bundle_path column

15. Evaluate and decide on Cursor sidecar

Medium

The Cursor sidecar (cursor-sidecar/, @cursor/sdk v1.0.12) is a live Docker service in production with its own billing and API surface. Decide before Phase 2 whether it's a core path or a development experiment. If core: add the same tracing, rate limiting, and health monitoring as other assistant modes. If experimental: remove from docker-compose.prod.yml to reduce attack surface and resource consumption.

deploy/docker-compose.prod.yml → cursor-sidecar service
