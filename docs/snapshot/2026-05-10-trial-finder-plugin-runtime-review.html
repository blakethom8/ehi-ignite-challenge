Trial Finder End-to-End Review

Snapshot date: 2026-05-10 · Scope: how one installed plugin is rendered, executed, and governed in the current Atlas shell.

This report traces Trial Finder from manifest to UI to backend run execution, then calls out the architecture changes worth considering before we lean on this runtime as a production-grade extensibility surface.

One Vite app Manifest-driven UI FastAPI runtime Consent + approval gates SQLite-backed run state

Executive Read

The current implementation is not a separate plugin frontend runtime. Plugins do not ship their own React/Vite bundles. Instead, the main application reads a signed-ish manifest, renders known home/workbench surfaces from that manifest, and calls a FastAPI plugin runtime for all live state changes.

For trial-finder, the manifest declares the trust posture, anchor scope, connectors, workflows, tools, tabs, and files. The frontend turns that into a shared workspace shell. The backend creates a run, compiles an anchor package, enforces consent and outbound approval, executes tools, stores run canvas state, and emits events. The frontend then projects that runtime state back into tabs, files, and workbench renderers.

What is working well in the current design The trust-sensitive behavior lives on the server. The frontend is primarily a projection layer, and the same five-pane shell can host both Caspian and plugin sessions without splitting the UX into two apps.

The source of truth is the manifest at data/plugins/trial-finder/2.4.1/manifest.json. It declares:

End-to-End Flow

  1. The plugin home page is rendered from the manifest.
    PluginHome.tsx reads manifest.ui.homeSections, manifest.workflows, and permissions metadata to build the home view with no plugin business logic in the component itself.
  2. Starting a run calls the backend runtime, not a client-side session builder.
    In Workspace.tsx, clicking a workflow triggers pluginsApi.startRun(), which posts to /api/plugins/runs.
  3. The backend creates a durable run record and anchor package.
    runtime.py loads the manifest, creates a run id, compiles the anchor package, stores the run in SQLite, and emits run.started. For Trial Finder, the initial state is awaiting-consent.
  4. The live route re-enters the shared workspace shell.
    The frontend route /workspaces/trial-finder/sessions/r_* is recognized as a live run and rendered through WorkspaceFrame, not a separate plugin panel.
  5. Live state is polled from FastAPI.
    usePluginRun.ts polls run status, event history, and approvals every two seconds, then builds a canvas map from persisted run canvas plus tool.result events.
  6. The operator flow sits in a plugin-specific chat pane.
    PluginRunChatPane.tsx shows the consent card, tool buttons, approval card, revoke action, and event trace. It is specialized UI inside the shared chat column.
  7. Server-side permission checks decide whether a tool can run.
    dispatch_tool() enforces read-anchor scope, connector declarations, and outbound approval requirements before calling the actual tool implementation.
  8. Tool results are persisted back into the run canvas.
    Non-outbound tools write their result to the run canvas and emit tool.result. Outbound tools first create an approval request, then on approval also write provenance and a final result payload.
  9. The frontend turns runtime state back into tabs and files.
    pluginRunWorkspace.ts projects the live run canvas into workbench tabs, file-tree nodes, artifact tabs, and anchor-derived previews like diagnoses.md.
  10. Renderers are still app-owned, not vendor-owned.
    The manifest can request trial.board or markdown.doc, but those renderer keys resolve through the central renderer registry already compiled into the main React app.

Current Architecture, Plainly

What is dynamic today

  • Manifest content: workflows, permissions, declared connectors, tabs, files, home sections.
  • Runtime state: runs, approvals, events, canvas payloads, provenance rows.
  • Artifact emergence: outbound or draft tools can create new artifact tabs during a run.

What is still app-coded today

  • Renderer implementations and registry keys.
  • Plugin operator recipes in PluginRunChatPane.tsx.
  • Canvas projection logic in pluginRunWorkspace.ts for each known plugin id.
The key architectural reality This is a manifest-driven plugin experience, but it is not yet a fully generic plugin platform. The platform still contains plugin-specific frontend projection logic and built-in renderer ownership.

Things To Consider In Production

The list below is intentionally opinionated. These are the architecture changes most likely to matter if this plugin surface moves from compelling demo/runtime into a trustworthy production capability.

1. Replace trusted request bodies with real auth and server-side identity.
The router currently trusts a user payload from the caller. That is fine for v1 local demos and not acceptable once approvals or outbound actions carry real clinical authority.
2. Move live run state from polling to event streaming.
usePluginRun.ts polls every two seconds. That is serviceable now, but approval-heavy or long-running workflows will want server-sent events or websockets plus explicit state transitions.
3. Separate plugin runtime execution from the API web process.
Tool execution is in-process today. If third-party plugins become real, we should think in terms of worker isolation, job queues, timeouts, memory budgets, and an execution boundary stronger than Python function dispatch.
4. Shrink the amount of plugin-specific projection logic in the frontend.
pluginRunWorkspace.ts contains per-plugin branches that synthesize derived files and tabs. That scales poorly if the plugin count grows. The platform should gradually move toward a typed artifact schema and manifest-declared view bindings.
5. Treat artifacts as first-class runtime objects, not just canvas payloads.
Right now artifact tabs are inferred from canvas values. A cleaner production model would give artifacts stable ids, lifecycle states, MIME/content types, provenance links, and access-control metadata.
6. Upgrade run storage beyond local SQLite assumptions.
SQLite is fine for this stage. Production likely wants a multi-user persistence story, row-level auditability, migration discipline, backup strategy, and a clean model for concurrent approvals and run updates.
7. Formalize connector secret management and outbound policy.
Connector declarations are present, which is good. Production also needs secret injection, request signing, destination allowlists, rate limits, and clear observability for every external call path.
8. Tighten manifest lifecycle management.
The manifest contract is already strong. The next jump is install-time verification, version pinning, upgrade rules, deprecation strategy, and a proper registry/distribution story rather than repo-local bundles only.
9. Make approvals and provenance independently queryable audit objects.
The basics exist. Production review, compliance, and incident response will want filtered audit search, export, immutable provenance retention, and a durable linkage between approval text, payload preview, outbound endpoint, and final artifact.
10. Add plugin capability classes, not just individual tool permissions.
The current permission model is clean and understandable. Over time, it will likely need richer policy dimensions: sensitivity tier, PHI class, outbound destination class, clinician role restrictions, and patient-consent provenance.

Architecture Changes Worth Prioritizing First

Near term

Auth, approval identity, and audit hardening. If there is one thing to stop treating as demo-only, it is caller identity for consent and outbound approval decisions.

Next platform step

Artifact model and event transport. A generic artifact contract plus streaming state would remove a lot of frontend glue and make runs feel like a real runtime, not a polling dashboard.

Before ecosystem scale

Execution isolation and manifest/registry lifecycle. Once plugins are not all authored by us, the process boundary and installation model become central, not optional.

Bottom Line

The current system is a strong architectural middle ground: one shared app shell, manifest-driven plugin UX, and backend-enforced trust boundaries. That is the right shape for where the product is today.

The main production question is not whether the shell model works. It does. The question is how fast we want to move from three built-in plugins with some platform branches to a genuinely extensible runtime with cleaner contracts, stronger isolation, and harder guarantees.

If we do nothing else before production Eliminate client-supplied authority for consent and approval actions, and stop assuming the web process is the right place to execute third-party plugin behavior.
