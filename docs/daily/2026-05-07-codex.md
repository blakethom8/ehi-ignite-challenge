## PDF / Document Pipeline Findings

### What Metriport Does

Metriport accepts and retrieves medical documents, stores them in S3, links them to FHIR `DocumentReference` resources, and exposes signed download URLs.

The core document lifecycle is:

1. Query HIE networks or accept customer upload.
2. Create or update `DocumentReference`.
3. Store raw file in S3.
4. Detect file MIME/type from content.
5. Convert XML/CDA documents to FHIR when possible.
6. Convert XML/CDA to HTML/PDF for visualization/download.
7. Index only XML/text/HTML-like documents for full-text search.

### What Metriport Does Not Appear To Do

No evidence found of a production PDF OCR/text-extraction pipeline using tools like:

- AWS Textract
- Tesseract
- `pdf-parse`
- PDF.js text extraction
- generic OCR-to-clinical-FHIR extraction

PDFs are accepted and preserved, but they are not generally parsed into structured clinical facts in the main open-source pipeline.

### Design Lessons For EHI Ignite

Metriport's document lifecycle is useful:

- Make every uploaded/retrieved source durable first.
- Represent the source as a FHIR `DocumentReference`.
- Keep source files addressable even when parsing fails.
- Use explicit document status transitions: preliminary, final, failed, superseded.
- Separate raw document storage from parsed clinical resources.
- Treat rendered PDF/HTML as a view artifact, not as the source of truth.

But EHI Ignite should go further on PDFs:

- Extract PDF text and layout.
- Add OCR fallback for scanned documents.
- Preserve page-level and bounding-box provenance.
- Convert extracted facts into reviewable FHIR-like resources.
- Track parser confidence and validation errors.
- Keep failed or uncertain extractions in a review queue rather than dropping them.

## Aggregation / Harmonization Findings

### Metriport's Aggregate Pattern

Metriport builds durable consolidated patient bundles. This is the strongest architectural reference for us.

Their flow is roughly:

1. HIE document query downloads `DocumentReference` files from CommonWell/Carequality.
2. XML/C-CDA documents trigger CDA-to-FHIR conversion.
3. Converted per-document bundles are stored on S3.
4. A consolidated builder merges conversion bundles, document refs, labs, pharmacy, structured extraction, and ADT resources.
5. The system stores a "with duplicates" bundle.
6. It deduplicates in a resource-specific and reference-aware order.
7. It normalizes/hydrates codes and units.
8. It stores the final consolidated bundle.
9. It indexes structured FHIR resources into OpenSearch.
10. Query APIs return filtered slices and rehydrate missing references.

### Strong Patterns To Bring Into EHI Ignite

1. Durable aggregate snapshots

   Do not rely only on API-time joins. Build a persisted patient aggregate that downstream modules can trust.

2. Intermediate artifacts

   Preserve distinct stages:

   - raw source
   - parsed bundle
   - with-duplicates aggregate
   - deduped aggregate
   - normalized aggregate
   - published clinical snapshot

3. Source attribution everywhere

   Every derived resource should carry enough provenance to answer:

   - which source file produced this?
   - which page/section/row produced this?
   - which parser or adapter produced this?
   - was this human-reviewed?

4. Reference-aware deduplication

   Deduping clinical resources is not just key-based merging. It requires ordered resource handling, reference rewriting, and dangling-reference cleanup.

5. Filter then rehydrate

   When returning a filtered slice, add back clinically necessary referenced resources so the slice remains readable.

6. Separate search indexes

   Keep structured resource search separate from raw document content search.

7. Idempotent rebuilds

   Rebuild the aggregate cleanly when upstream data changes. Delete or supersede old search/index artifacts rather than layering uncertain state.

## Application Guidance

### Near-Term Architecture Direction

For EHI Ignite, the next version of our ingestion and harmonization architecture should look like:

1. Source Intake stores every source as a durable source artifact.
2. Each source gets a `DocumentReference`-like metadata record.
3. Format detection decides parser route by MIME/content shape, not filename only.
4. Parsers emit source-scoped bundles plus provenance.
5. Harmonization produces staged canonical facts.
6. Review Queue resolves uncertain facts.
7. Publish Chart creates the active clinical snapshot.
8. Downstream pages read only the active published snapshot.

This aligns with our current app direction, but Metriport reinforces the value of making the intermediate artifacts more explicit.

### PDF Parser Direction

Metriport does not solve the PDF parsing problem we care about. That remains a core EHI Ignite wedge.

Our parser should prioritize:

- PDF text extraction where available.
- Vision/OCR fallback for scanned pages.
- clinical section detection.
- page and bbox provenance.
- FHIR-shaped outputs.
- validation without silent drops.
- human review for ambiguous facts.

### Harmonizer Direction

Borrow the architecture pattern, not code:

- Keep the aggregate artifact durable.
- Add explicit aggregation stages.
- Add source and parser metadata to every fact.
- Move toward resource-specific dedupe rules.
- Add reference cleanup where we emit FHIR resources.
- Keep published snapshot boundaries strict.

### Search Direction

Metriport's split search model is useful:

- Document text search answers: "Which source document contains this phrase?"
- Structured clinical search answers: "Which normalized clinical facts match this concept?"

For EHI Ignite, this maps naturally to:

- source/document evidence search
- clinical fact search
- assistant retrieval over active published snapshots

### Product Differentiation

Metriport is infrastructure. EHI Ignite should remain a clinician workflow.

The product should not become a generic FHIR browser or HIE API. The backend can learn from Metriport, but the UI should stay focused on:

- fast chart review
- medication risk
- surgical/specialty readiness
- explainable source-backed facts
- clean publishable chart snapshots

## Proposed Follow-Up Packets

### Packet 1 - Format Detector

Create a formal format detector for Source Intake:

- MIME sniffing
- extension fallback
- JSON shape validation
- FHIR Bundle detection
- XML/C-CDA detection
- PDF scanned/text-layer classification if feasible
- parser-route explanation in UI/API

### Packet 2 - Source Artifact Model

Make durable source artifacts more explicit:

- source id
- original filename
- MIME/content type
- storage location
- parser status
- parser selected
- parse attempts
- checksum
- source-to-fact lineage

### Packet 3 - Snapshot Stage Artifacts

Persist or expose clearer stages:

- raw parsed bundle
- normalized bundle
- harmonized staged facts
- reviewed facts
- published snapshot

### Packet 4 - PDF Extraction Deepening

Add or plan:

- text-layer extraction
- OCR fallback
- page event callbacks
- section-aware extraction
- candidate/draft fact preservation
- reviewer rescue path

### Packet 5 - Resource-Specific Dedupe

Start with the highest-value resources:

- medications
- conditions
- allergies
- labs/observations
- encounters

For each, define:

- matching keys
- date/window logic
- code/text equivalence
- source preference rules
- merge behavior
- review triggers
