§1Synthea round-trip — does it bias us toward agents?

This is a sharp question and worth being precise about. There are two distinct biases to worry about, and they're not equally severe.

Generator bias — smaller than it sounds

Synthea is rule-based, not LLM-generated. The bundles come from a Java state machine (MITRE's open-source project) that simulates patient lifecycles using clinical ontologies and evidence-based care pathways — sepsis protocols, diabetes progression, immunization schedules. No agent in the loop. So the worry "are we testing whether our pipeline can invert another agent's output?" is largely answered by the architecture: we'd be testing whether we can invert a renderer (HTML/CCDA → PDF), not an LLM.

That said, the rule-based generator does have its own clinical model — it knows what conditions co-occur, what medications follow which diagnoses, etc. If our pipeline learns the shape of typical Synthea co-occurrence, it might over-predict on real PDFs that violate those patterns. This is a real but small effect, and it's mostly fixed by also evaluating against atypical real PDFs.

Distribution bias — the bigger problem

The harder issue is that Synthea PDFs are too clean. Real EHI exports include:

  • Faxes and scans with dropped pixels and skew
  • Multiple-column layouts that confuse reading order
  • Redaction stamps on top of text
  • Copy-pasted prior-records sections with stale dates
  • Handwritten annotations on printed forms
  • OCR layers from older PDFs that disagree with the visual layer

Synthea has none of this. Tune to it and we tune to the easier half of the distribution. The F1 number won't transfer to a real Cedars or Kaiser export.

So what's Synthea actually for?

I'd reframe it. Synthea is best as a regression test, not a benchmark. It tells us "the pipeline doesn't break on machine-clean clinical content with a known answer." It doesn't tell us we're production-ready. The headline benchmark needs to be a small set of human-annotated real PDFs.

Where Synthea earns its keep: scale and edge cases. 1,180 free test cases. We can ask things human-annotation can't reach — what happens when there are 50 medications? When the patient has 30 years of records? When immunizations span two CVX systems? Synthea is the dense bench for unit-test-style sanity; human-annotated is the headline metric.

Practical implication

The "trustworthy GT" stack is probably three layers: Synthea round-trip (broad sanity, free, knowable answer); cross-model agreement on real PDFs (medium scale, still LLM-shaped); a small human-annotated golden set of ~10–20 real PDFs (the only one we can publish a number against without caveats). All three contribute different signal.

§2The codex / Claude-Code subscription experiment

This thread is more interesting than it first looks. The instinct: today's perf pass cost ~$1.50 in API calls plus my orchestration time. If we ran the same work through a Claude Code Max subscription or a Codex CLI session, the marginal cost is zero — the subscription absorbs it. So a test bench that costs $50 in API becomes ~free if developers run it through a subscribed agent session.

What we'd actually learn

  • How subscription economics shift the bench-design calculus. Running 1,000 PDFs through 5 pipelines is $50 in API and ~free in a subscription. The "what should we benchmark" question becomes unbounded. Different products fall out — instead of "F1 on 5 PDFs" we get "F1 distribution across 1,000 PDFs with confidence intervals."
  • Where rate limits hit. Multi-pass extraction is bursty: 13 parallel calls per PDF. Subscriptions are designed for interactive coding, not batch eval. We'd find the cliff fast and learn the practical batch size.
  • What an autonomous bench-running loop looks like. Codex CLI / Claude Code can iterate: run pipeline → score → tweak prompt → re-run, all under one subscription budget. This is a different mode than today's "human dispatches build agent" pattern.

The second-order point

There's a second product wedge here beyond FHIR extraction: the bench as a subscription-friendly artifact.

If we ship the bench as a CLI that runs against any of (Claude Code, Codex, raw API), the user picks the budget shape. That's a real differentiator vs LlamaParse / Reducto where pricing is per-page and rigid. "Bring your own agent subscription" is a positioning we can credibly occupy.

Concretely worth trying: open a Codex session, point it at the existing lab CLI, ask it to run 10 PDFs through 3 pipelines and report. Either it works (and we have a new ops mode) or it hits rate limits (and we learn the practical ceiling). One session, real data.

§3Existing clinical-NLP parsers — the best-of-breed → FHIR adapter

This is the right instinct. There are clinical-NLP tools that are SOTA on specific tasks, and none of them speak FHIR natively. Our value-add becomes the FHIR shaper, not the extractor.

The candidates

Tool What it does Output Cost
AWS Comprehend Medical Clinical NER (Medication, Condition, Anatomy, ProtectedHealthInformation, etc.) JSON entities with offsets, confidence, RxNorm/ICD10/SNOMED links ~$0.01 / 100 chars
Azure Text Analytics for Health Same shape; recently added FHIR-emit option JSON entities; optional FHIR R4 bundle per char, free tier
Google Healthcare NLP API Medical concept extraction with UMLS linking JSON entities per char
MedCAT OSS biomedical NER with UMLS linking; trainable JSON entities, configurable free, self-host
cTAKES OSS Mayo Clinic full clinical NLP pipeline; older but battle-tested UIMA CAS XML, includes negation/temporal free, self-host
CLAMP Vanderbilt clinical concept extraction, UMLS-linked configurable free for academic

The architecture this enables

Vision → markdown (MinerU) → entity extraction (Comprehend Medical) → FHIR adapter (us) → validated bundle. Each stage is best-of-breed, and we own the FHIR layer plus the bench. The pipeline becomes a composition we can configure per content type — vision + LLM for narrative-heavy clinical notes; markdown + Comprehend Medical for tabular lab reports; cTAKES for legacy formats with negation-rich language.

The repositioning

We're not "the best PDF parser." We're the best FHIR-shaper, and we'll happily plug into whichever extraction backend is best for this content. The bench validates the choice per content type.

This is actually a stronger position than "we built the extractor." Extractors are commoditizing fast — every quarter another model or another OSS tool ships. FHIR-shaping (clinical semantics + US Core compliance + Provenance graph + episode reconstruction) is the durable craft.

§4The bench as the platform

This is the most interesting thread you raised. Let me articulate what I think you're pointing at.

Today, every team that wants to do PDF→FHIR is reinventing the wheel. There's no shared bench, no shared GT, no public leaderboard. Every team writes its own evals against its own PDFs and reports its own F1 in a way that doesn't compare to anyone else's number. (Look at any vendor marketing page — F1 numbers everywhere, none comparable.)

The meta-position

If our codebase becomes "the place where you bring your pipeline and we tell you how it does on shared clinical PDFs," we capture a meta-position: not the best extractor, but the arbiter of who's the best. Like ImageNet for clinical PDF extraction. The most valuable real estate in any benchmark domain is the benchmark itself.

What a good bench needs

  • Clear test set — mix of real annotated PDFs, Synthea round-trip, edge cases (multilingual, multi-encounter, scanned, etc.)
  • Plug-in architecture — any pipeline that emits FHIR can be tested. Today's ExtractionPipeline Protocol is already close.
  • Diagnostic outputs — not just F1; per-resource-type breakdowns, failure-mode taxonomies, latency, cost-per-PDF
  • Cost transparency — everyone reports cost-per-PDF too. Without it, expensive pipelines look unfairly good.
  • Reproducible — same PDF + pipeline + version → same result, modulo LLM determinism. Versioned with hashes.
  • Public leaderboard — a website where new pipelines get scored automatically and ranked.

Status

We have most of these. The protocol exists, the lab CLI exists, the eval harness exists, versioned GT exists. What's missing:

  • A small set of human-annotated real PDFs (the GT problem from §1)
  • More than 3–4 pipelines plugged in (the §3 work)
  • A public leaderboard view (frontend work)
  • A way for outsiders to submit a pipeline (probably a Docker container interface)

This is genuinely a 1-2 week sprint to ship as v1, and it's something nobody else has shipped. The challenge submission positions naturally as "a bench, an extractor that uses the bench, and a clinical UX on top." Three layers, all defensible, mutually reinforcing.

§5D2C FHIR — what does standardization actually buy?

Short answer: yes, but the leverage is uneven across consumer use cases. The longer answer matters because it shapes what we build first.

Where FHIR actually plugs in

Channel Accepts patient FHIR upload? Notes
Apple Health Records / CommonHealth No — read-only from authenticated EHR Native FHIR consumers but the trust path is the EHR's auth, not arbitrary uploads
Carequality / CommonWell / eHealth Exchange No — clinical-to-clinical only Patient-uploaded data isn't accepted; needs a participating provider source
CMS Interoperability APIs (payer) Read-only for members Members pull their data; we can't push to it
EHR ingestion at point-of-care Theoretically yes; practically per-EHR friction Most EHRs reject anything without a recognized provider source
Research portals / clinical trials Yes — many accept patient FHIR bundles Real but low-volume use case
Telehealth / second-opinion Increasingly yes Not bound by legacy EHR ingest constraints

What this means for product

The practical D2C use cases for our extracted FHIR are mostly internal to our own surfaces:

  1. Personal health record consolidation. Patient gathers all their PDFs from various sources, we extract, we present a unified longitudinal view. FHIR is the internal format that makes this work; the user never sees it.
  2. Pre-visit briefing. Patient brings the unified record to a new specialist. Today: "here's a folder of PDFs." Tomorrow: "here's a 5-fact briefing derived from FHIR." The receiving EHR can't ingest our FHIR — but the physician can read our briefing. This is your north star.
  3. Episode reconstruction across sources. Cedars + Kaiser + a sleep clinic and a cardiology consult — FHIR makes deduplication and linkage tractable in a way "PDFs in a folder" never will.

The reframe

FHIR's value in D2C is less "plug into existing exchanges" and more "lossless intermediate format for our own product surfaces." The exchange story is real but slower-moving — driven by regulation (TEFCA, the CMS Final Rule) over years.

We don't need exchanges to be valuable. We need the patient to walk into an appointment armed with something the physician can absorb in 30 seconds — which requires the data to be structured, deduplicated, linked, and ranked. FHIR is the format that makes that possible internally. Whether we ever push to a HIE is a question for year 3, not year 1.

§6Where this lands

The five threads converge on one observation: we're not building a PDF parser. We're building a clinical-data validation platform, with a strong PDF parser as one of its loaded components, a bench as its meta-position, and a 5-fact clinical briefing as its consumer-facing wedge. FHIR is the spine connecting all of these.

If that framing is right, the priority order changes:

  1. GT trust is the foundation. Synthea round-trip + a small human-annotated set + cross-model agreement. Without trustworthy GT, none of the rest of the bench means anything. ~3 days
  2. Multi-pipeline plug-in architecture. Wire MinerU + LlamaParse + Comprehend Medical as alternative extractor backends, all funneling into our FHIR adapter. The bench becomes a real comparison tool. ~2 days
  3. Subscription experiment. One Codex / Claude Code session running the full bench. Learn the rate-limit cliff and the operational mode. ~half a day
  4. Local Gemma 4 backend. $0/PDF unlock if it works; falsifiable hypothesis about Move F's chunking regression. ~1 day

What I'd ask back

The "bench as the platform" framing — does it match what you've been seeing as the wedge? The $490K Phase 1 prize rewards "innovative applications that transform EHI" — the bench framing reads as infrastructure, which is harder to pitch as application but easier to defend long-term.

The other open question is the FHIR-shaper-not-extractor positioning. It means de-emphasizing "our extractor" and emphasizing "our FHIR semantics + Provenance + episode reconstruction." That's a real strategic shift. Genuinely interested whether that lands or whether you'd rather lead with extraction quality.
