Atlas Wedge · Cross-source Merge with FHIR Provenance

One canonical record. Every fact knows where it came from.

The harmonize layer takes per-source FHIR resources from heterogeneous ingestion paths (native FHIR pulls + vision-extracted PDFs), identity-resolves them, and emits one merged record per canonical fact — each with a Provenance edge pointing back at every source observation that contributed. Below: the data model, the merge identity priorities, and how data actually flows from disk through the matcher to the React app.

§ 1Anatomy of a merged record

Every merged record is one canonical clinical fact (a lab, a condition, a med, an allergy, an immunization event). The shape is consistent across resource types; only the identity-priority list differs.

Top-level dataclass · MergedObservation

canonical_nameHuman-readable lab name (from the LOINC bridge, or the source's display text)
loinc_codeLOINC code if known (else None for unbridged)
canonical_unitTarget unit values are normalized to (e.g. "mg/dL")
sourcesList of ObservationSource — every source measurement, oldest first
provenanceList of ProvenanceEdge — one per source contribution
.latestProperty: most recent source measurement
.has_conflictProperty: same-day cross-source disagreement > 10 %

Per-source dataclass · ObservationSource

source_label"Cedars-Sinai (FHIR)" / "Function Health · 2024-07-29" / etc.
source_observation_refFHIR ref back to the original Observation
valueNumeric value, normalized to canonical_unit
unitApplied unit after normalization
raw_value, raw_unitOriginal source values, preserved verbatim
effective_dateWhen the measurement was made
document_referencePointer to the source document (PDF or FHIR pull)

§ 2Five resource types · USCDI v3 clinical-summary core

All five matchers share the architecture above. Identity priority differs per type because the canonical code system differs (LOINC for labs, SNOMED for conditions, RxNorm for meds, CVX for vaccines, mixed for allergies).

§ 3Forward pipeline · sources → merged record

What happens when the React page loads or after the user clicks Extract. Five lanes, one direction.

① On disk

FHIR pulls + extracted-PDF JSON files in:

data/synthea-samples/
data/harmonize-demo/
data/aggregation-uploads/<session>/
ehi-atlas/corpus/.../blake_records/

② Collection registry

api/core/harmonize_service.py

Static (synthea-demo, blake-real conditional) + dynamic discovery (upload-<session>).

Returns CollectionDefinition with N SourceDefinitions.

③ Loader

_load_resources_by_type()

Reads each source's JSON file, returns {ResourceType: [resource, …]}. Mtime-cached via lru_cache.

④ Matcher

lib/harmonize/<type>.py

For each input resource: extract codes + name + date, resolve identity by priority, normalize units (Obs only), append to MergedX.sources.

⑤ Provenance

lib/harmonize/provenance.py

One ProvenanceEdge per source contribution; FHIR Provenance resource minted on demand for the per-fact lineage panel.

§ 5Two directions of the Provenance graph

The same edges power two different clinician questions. Forward: per-fact lineage. Reverse: per-source contribution.

Forward · per-fact lineage

"Where did this fact come from?"

User clicks a row in the Labs / Conditions / Medications / Allergies / Immunizations table. The Provenance panel populates with the source edges for that one fact.

GET /api/harmonize/{collection}/provenance/{merged_ref}
Response: a single FHIR Provenance resource, one entity per contributing source, with source-label + harmonize-activity Atlas extensions on each.
Reverse · per-source contribution

"What did this PDF contribute?"

User clicks a row in the Sources panel. An inline panel expands showing every merged fact this source touched, partitioned by resource type.

GET /api/harmonize/{collection}/contributions/{document_reference}
Response: counts + lists across all 5 resource types. Cedars FHIR contributes 207 facts on blake-real (174 obs + 15 cond + 7 med + 1 all + 10 imm); Cedars PDF contributes 160.
