Navigation and First-Open UX Review

This review covers the current app navigation, the first page users hit in each major module, and the gating rules needed so patient data does not appear before login or explicit demo-patient selection.

Bottom line: The app currently behaves like a set of connected surfaces for an already-in-context internal user, not like a controlled first-time-user product. The biggest problems are inconsistent start pages, dropped patient context during top-bar navigation, and the lack of a true access gate before chart data flows.

What Is Working

The app has a coherent five-module frame and several module-local overviews already exist.

Landing Patient Record Overview FHIR Charts Overview Plugins Index Caspian Shell

The module-local sidebars in Patient Record and FHIR Charts already preserve patient context via ?patient=, which is the right behavior inside a module.

What Is Broken

  • Top-bar module switching does not preserve patient context.
  • Some top-bar affordances are nonfunctional placeholders: search, help, and drawer actions.
  • Module entry points are inconsistent: some open an overview, some open a live shell, some open internal tools.
  • The app root still acts like a marketing/overview page, not a controlled access gate.
  • There is no real auth gate; demo/mock access is implicit rather than explicit.

Primary Findings

1. Context is fragile. The current design depends on ?patient= in many local links, but the global shell does not honor that contract.
2. Start states are inconsistent. Patient Record and FHIR Charts open overview pages, Caspian opens a live workspace, Plugins opens a marketplace, and Learn opens internal tools.
3. Orientation happens too late. In several flows the user first sees a dense shell, then sees a no-patient warning inside it.

Design Principle Going Forward

The correct model is: access gate first, module start page second, dense workspace third.

  • Users should never fall into a deep workspace before choosing how they are entering.
  • Patient context should be a first-class global state, not a fragile URL convention.
  • Demo mode should be explicit and visible.
  • Internal tools should not compete with clinician-facing modules in the top bar.

Recommended Global Navigation Model

Top-Level Item Role Recommended First Open

Learn Internal docs and evaluation tools Remove from primary clinician nav; move to menu or admin/internal mode

Recommended First-Open States

App Root

Show a controlled entry page with two primary actions: Sign in and Continue with demo patient.

Patient Record

If no patient is active, show a start page explaining intake, harmonization, and publishing with a patient-selection CTA.

Chart Review

If no patient is active, show a chart-review start page rather than partial empty widgets and disconnected “no patient selected” states.

Caspian

Open a Caspian start surface first: what it does, what it requires, and a clear button to choose a patient before opening the full shell.

Plugins

Marketplace can remain open without a patient, but starting a plugin run should require active patient context and explain why.

Internal Tools

Keep internal tools behind a separate navigation layer. They should not be mistaken for the normal first-time-user experience.

Access and Gating Rules

User State What They Can See What Must Be Blocked
Signed out Home gate, product framing, sign-in CTA, demo-patient CTA Patient pool, real patient charts, live Caspian patient sessions
Demo mode Demo patient surfaces with a visible “Demo” banner and explicit patient badge Any ambiguity about whether the user is viewing real or demo data
Authenticated, no patient selected Module start pages, marketplace browsing, patient selector Chart-specific data views and run start actions that require a patient
Authenticated, patient selected All module overviews, chart review pages, Caspian, plugins with proper trust gating Silent patient-context loss when moving between modules

Implementation Guidance

  1. Create a global patient-context store. Stop treating ?patient= as the primary cross-module state mechanism.
  2. Add an access-gate route layer ahead of module roots. Root routes should decide between login, demo mode, patient selection, and module content.
  3. Introduce module start pages for /patient-record, /fhir-charts, and /caspian when there is no active patient.
  4. Preserve active patient context when top-bar navigation or workspace switching occurs.
  5. Make demo mode explicit in UI and routing, rather than relying on API fallback behavior.
  6. Move Learn out of the primary clinician navigation or clearly label it as internal.
  7. Replace placeholder top-bar actions with real routes or hide them until implemented.

Recommended Delivery Sequence

  1. Fix top-bar patient-context preservation first. This is the most immediate broken-navigation issue.
  2. Introduce an explicit access gate and demo mode entry at the app root.
  3. Add module start pages for Patient Record, Chart Review, and Caspian.
  4. Move internal-only surfaces out of the primary nav.
  5. Add regression tests for module switching, no-patient entry states, and demo-vs-real gating.

Definition of Done for the Redesign

The redesign is successful when a first-time user can enter the app, choose either authenticated or demo mode, understand each module before entering it, and move between modules without losing patient context or landing in dense workspaces prematurely.
